## Evidence and vocabulary

- **Source-confirmed:** inspected application code, Prisma schema and checked-in migrations. These do not prove the deployed database is identical or that external jobs do not exist.
- **Provider-documented:** public official documentation, retrieved October 23, 2026. This is not verification of Wings4U's subscription, configuration, contract or data inventory.
- **Owner confirmation:** evidence requiring a separately authorized person/account review.
- **Unknown:** not established by available source/public documentation.

Logical expiration means a record stops being accepted; it does not imply physical removal. Physical deletion removes live rows/local entries, but not every backup or external copy. Account-deletion cleanup can physically delete some categories and erase/minimize fields in retained financial/operational records. Tombstones and linked transaction IDs remain **pseudonymous**, not guaranteed anonymous. Financial/legal retention needs a documented purpose and period; no statutory period is invented here.

## Source details that change the cleanup design

1. Saved cart identity is scoped to owner **and location and status**. The schema allows null owner fields and does not declare an exactly-one-owner CHECK in the cart migration. Mixed owners, no owner and blank guest tokens must be quarantined. Unique indexes do not substitute for this validation.
2. Only `saved_cart_items.cart_id` is declared to cascade when a cart is deleted. `saved_carts` points to users/locations with NO ACTION, and items point to menu items with NO ACTION. Deleting a cart does not cascade upwards into a user, location or menu. No Order-to-SavedCart FK is declared in the inspected schema. Deployed/custom FKs, triggers and JSON/application references still require owner verification.
3. Null-expiry fallback uses `updated_at`, not `created_at` or scan time. GETs/no-op usable saves do not refresh the deadline. Source constants use fixed milliseconds: SQL should use 168/720 hours, not timezone-sensitive calendar-day arithmetic.
4. No API production writer for ABANDONED was found. `clear` changes usable carts to CONVERTED and may remove the old CONVERTED slot; do not infer every CONVERTED row has a corresponding completed order. Existing conversion cleanup must not be silently broadened.
5. The public cart response changes after physical deletion: missing row differs from an expired row. Current clients intentionally recover some fresh unsaved drafts when the server is empty/unavailable. This is a **proposed-cleanup compatibility risk**, not proof of a current restoration bug. Staging tests must demonstrate correct behavior before a purge is approved.
6. Sign-up rate limits include a device window of three creations per seven days, IP hourly/daily limits and email controls. Device keys are hashed; Redis windows have TTLs and an in-process fallback. Rotating an ID can reset the device bucket, so a 180-day interval and upgrade behavior require anti-abuse review. The ID is not an unresettable hardware identity.

## Account deletion consistency

Account deletion is **implemented and documented as enabled in production**. Existing dated evidence reports `enabled: true`, policy version `2026-10-20-review-2`, on October 23, 2026. This task did not contact that endpoint or the database again. Historical rollout instructions are not evidence that activation is pending.

The inspected cleanup matches the principal matrix: owned carts/addresses/sessions/identities are deleted; wallet/rewards obligations are protected; order/payment/support text is removed or minimized; financial/operational links and a sealed inactive User tombstone remain. A serializable deletion transaction locks the User, rechecks blockers, consumes authorization and commits erasure/minimization atomically. Migration triggers guard later writes to deleted owners and reapply minimization on retained records. No deletion code was changed or executed.

Real evidence gaps remain: approved retention/purge schedules, provider/backup handling, hold intake/operations, staging scale/concurrency results and independently exercised real deletion. These do not make the implemented feature unfinished. Terminal UNPAID/FAILED order summaries alone do not trigger the nonterminal outstanding-payment blocker; pending transaction/refund/hold checks remain independent. The cart-only proposal does not erase any of those records or resolve an obligation.

Documentation drift to consider separately: the deletion matrix's external-provider row still uses historical activation-blocker language, and its mobile Stripe description predates [commented-out mobile initialization](stripe-dormancy.md). Current source cannot prove Stripe never held historical data, nor that external approvals were never given. Treat these as dated documentation/evidence limits, not new production defects or permission to change deletion behavior.

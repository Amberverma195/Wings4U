# P6 — Accessibility Audit & Fixes: Colour Contrast, Keyboard Navigation & Form Labeling

**Document Status:** Complete Audit Report & Applied Fixes  
**Target:** Wings 4 U Web Application (`apps/web`)  
**Scope:**
1. **Colour Contrast & Readability:** Red, yellow, black, and white colour combinations throughout the application evaluated against WCAG 2.1 AA standards (4.5:1 for normal text, 3:1 for large text).
2. **Keyboard Navigation & Popup Focus:** Mouse-free navigation (Tab, Shift+Tab, Enter, Space, Escape) across core journeys (Sign In, Browse Menu, Customize Wings, Cart, Checkout) and popup/modal focus containment.
3. **Form Field & Accessible Labeling:** Explicit association between `<label>` and `<input>` using `htmlFor` and `id` across customer authentication views (`customer-auth.tsx`) to guarantee screen reader identification (WCAG 2.1 Criteria 1.3.1 & 4.1.2).

* **Location:** [`globals.css:1578-1583`](file:///d:/Projects/Websites/Wings4U/Code/apps/web/src/app/globals.css#L1578-L1583)

## 3. Keyboard Navigation & Popup Focus Audit

### 3.1 End-to-End User Journeys (Mouse-Free)

1. **Sign in via keyboard (Tab, Shift+Tab, Enter, Space):**
   - `<form onSubmit={...}>` wraps all auth screens. Pressing `Enter` in the phone/email input or password input directly advances the flow.
   - Minor gap: Password show/hide toggle has `tabIndex={-1}` (`customer-auth.tsx:417`).
2. **Browse the menu:**
   - Category pills (`.wk-cat-btn`) are native buttons; Tab reaches them; Enter/Space activates `scrollToCategory()`.
   - Item cards have native buttons (`.menu-add-to-cart-btn`, `+`/`−`) reachable via Tab.
3. **Customize wings:**
   - Preparation options, heat level tabs, flavour pills, saucing options, and dips are native buttons reachable by Tab and selectable with Space/Enter.
   - Sticky footer quantity buttons (`−`/`+`) and "Add to order" submit button respond to Tab/Enter/Space.
   - `Escape` dismisses the builder.
4. **Cart and Checkout:**
   - Line items can be incremented, decremented, removed, or edited with keyboard.
   - Contactless preferences dropdown uses HeroUI ComboBox (accessible with Tab, Arrow Down/Up, Enter, Escape).
   - Payment options are `<button className="checkout-payment-option">` with `aria-pressed`.
   - "Place order" button triggers checkout; on order success, focus automatically jumps to `successPanelRef` (`checkout-client.tsx:611`).

### 3.3 Keyboard Focus Remediation Code

Create a customer-facing focus trap and modal hook modeled after the admin implementation:

```tsx
// apps/web/src/hooks/use-modal-dialog.ts
"use client";

import { useEffect, useRef, type RefObject } from "react";

export function useModalDialog({
  dialogRef,
  initialFocusRef,
  onClose,
  active = true,
}: {
  dialogRef: RefObject<HTMLElement | null>;
  initialFocusRef?: RefObject<HTMLElement | null>;
  onClose: () => void;
  active?: boolean;
}) {
  const onCloseRef = useRef(onClose);
  useEffect(() => { onCloseRef.current = onClose; }, [onClose]);

  useEffect(() => {
    if (!active) return;
    const dialog = dialogRef.current;
    if (!dialog) return;

    const previousFocus = document.activeElement instanceof HTMLElement ? document.activeElement : null;
    const previousOverflow = document.body.style.overflow;
    document.body.style.overflow = "hidden";

    (initialFocusRef?.current ?? dialog).focus();

    const getFocusable = () =>
      Array.from(
        dialog.querySelectorAll<HTMLElement>(
          'a[href], button:not([disabled]), input:not([disabled]):not([type="hidden"]), select:not([disabled]), textarea:not([disabled]), [tabindex]:not([tabindex="-1"])'
        )
      ).filter(el => !el.closest('[aria-hidden="true"]') && el.getClientRects().length > 0);

    const onKeyDown = (event: KeyboardEvent) => {
      if (event.key === "Escape") {
        event.preventDefault();
        event.stopPropagation();
        onCloseRef.current();
      } else if (event.key === "Tab") {
        const elements = getFocusable();
        if (elements.length === 0) {
          event.preventDefault();
          dialog.focus();
          return;
        }
        const first = elements[0];
        const last = elements[elements.length - 1];

        if (event.shiftKey && document.activeElement === first) {
          event.preventDefault();
          last.focus();
        } else if (!event.shiftKey && document.activeElement === last) {
          event.preventDefault();
          first.focus();
        }
      }
    };

    const onFocusIn = (event: FocusEvent) => {
      if (!dialog.contains(event.target as Node)) {
        const elements = getFocusable();
        (elements[0] ?? dialog).focus();
      }
    };

    document.addEventListener("keydown", onKeyDown, true);
    document.addEventListener("focusin", onFocusIn);

    return () => {
      document.removeEventListener("keydown", onKeyDown, true);
      document.removeEventListener("focusin", onFocusIn);
      document.body.style.overflow = previousOverflow;
      if (previousFocus?.isConnected) previousFocus.focus();
    };
  }, [dialogRef, initialFocusRef, active]);
}
```

## 4. Form Field & Accessible Labeling Audit & Fix (`customer-auth.tsx`)

### 4.1 Issue Description & WCAG Compliance
In [`apps/web/src/components/customer-auth.tsx`](file:///d:/Projects/Websites/Wings4U/Code/apps/web/src/components/customer-auth.tsx), several customer authentication and registration fields rendered visual text labels (such as "Full name", "Phone number", "Email", "Password", and "Confirm password"), but these labels were not programmatically associated with their corresponding `<input>` elements.

#### Relevant Standards:
- **WCAG 2.1 Criteria 1.3.1 Info and Relationships (Level A):** Information, structure, and relationships conveyed through presentation must be programmatically determinable or available in text.
- **WCAG 2.1 Criteria 4.1.2 Name, Role, Value (Level A):** For all user interface components (including form elements), the accessible name and role must be programmatically determinable.

#### Impact:
1. **Screen Readers (NVDA, JAWS, VoiceOver, Android TalkBack):** When a user focused an input via the `Tab` key, screen readers could not consistently announce what the field was for (e.g. announcing "edit text, blank" instead of "Email, edit text").
2. **Touch & Mouse Ergonomics:** Standard HTML behavior dictates that clicking or tapping an associated `<label>` transfers focus to the corresponding input or toggle. Without `htmlFor` and `id`, users clicking label text experienced no focus shift.
